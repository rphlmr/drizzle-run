# Schema fidelity corpus

One shared corpus, `cases.ts`, runs on every release. Each ORM API has a small entry that supplies the PostgreSQL
APIs spelled differently in that release (`PgReleaseApi` in `types.ts`) and exports the cases:

- `legacy.ts`: ORM `0.45.4`, Kit `0.31.11`.
- `next.ts`: ORM and Kit `1.0.0-rc.5`.

The corpus holds **28 PostgreSQL and 14 SQLite scenarios**, 42 per guest image, listed in `case-ids.json`. These are original,
focused fixtures guided by the [pinned documentation tree](https://github.com/drizzle-team/drizzle-orm-docs/tree/3a3ca242fbfe970566f830de8b0e5371fe7c7ad7/src/content/docs).
The docs are a coverage reference, not an oracle for expected SQL. That commit
also contains some V1 APIs, so fixtures are checked against the installed exact
release declarations rather than copied indiscriminately.

## Gate

Run `node testing/capability-harness/src/gates/kit-parity.gate.ts`
from the workspace root. The gate compiles each release's typed entry,
then runs the same source against the exact official Kit and ORM package tree in
native Node and the shipped QuickJS-WASI dependency bundle. It compares every PostgreSQL and SQLite
SQL-generation case of the corpus (42 per guest image) byte-for-byte. Every case must succeed;
the shipped pairs have no accepted upstream failures.

Each case builds a fresh schema graph. Statement order, whitespace, literal
text, and semicolons are compared unchanged. Nonempty cases must generate SQL;
empty schemas and existing-only views must generate no statements. Runtime hook
fixtures throw if Kit evaluates application callbacks. The guest corpus resolves its ORM imports through
the shipped bundle's module inventory, sharing ORM identities with Kit.

## Release-specific choices

- Binary columns use `customType` returning `bytea` on legacy, which has no native
  `bytea` export. RC5 uses native `bytea`.
- RLS without policies uses legacy `.enableRLS()` and RC5 `pgTable.withRLS()`.
- Same scenario IDs do not require legacy SQL to equal V1 SQL. Each release must
  equal its own official Kit with matching generation options.
- The imported timestamp helper in `helpers.ts` is shared and typechecked against
  each release. This tests composed schema objects and imported builders; it does
  not test the project compiler's virtual filesystem or alias resolver.

## Boundaries and maintenance

This is common-schema coverage for **fresh-database DDL generation**. It does not
claim every combination of options or all documented Drizzle functionality.

Not covered here: migration diffs on existing databases, introspection, push,
ORM relation-query execution, invalid-schema diagnostic equivalence, database
permissions/enforcement, PostgreSQL execution of every generated statement,
PostGIS, provider-specific integrations, or browser packaging/isolation.
One-to-one/one-to-many/many-to-many cases test their physical keys and tables,
not the version-specific soft-relations query APIs. Custom types test DDL shape,
not application value encoders/decoders.

Keep cases small and introduce a combined case when an interaction matters.
Add a case to `cases.ts` so every release runs it, and add its `<dialect>:<id>` to `case-ids.json`: the gate fails
when the compiled corpus or a pair's report differs from that list, so a dropped case cannot pass unnoticed.
When a release spells its API differently, add the API to `PgReleaseApi` and implement it in each entry rather
than silently dropping coverage. Do not update expected
snapshots or normalize away a discrepancy to turn the gate green. Investigate a
mismatch as a potential Drizzle Run defect, and retain the user-derived minimal
case before attributing a report upstream.

Fixtures are typechecked against each guest's drizzle-orm by `scripts/typecheck-corpus.ts` and excluded from the
harness build output. No
production dependency or public runtime API is introduced by this corpus.
