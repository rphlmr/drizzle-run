# Drizzle Run app

The Drizzle Run web app and its Cloudflare Worker. The app is React with Monaco and XState; runs go through
`@drizzle-run/runtime`, and the Worker serves the pages, the API and the runtime assets. See
[docs/architecture.md](../../docs/architecture.md) for how the pieces fit.

Run it from the repository root with `pnpm dev` (see the [root README](../../README.md#run-it-locally)). Hosting
and releases are in [docs/cloudflare.md](../../docs/cloudflare.md).

## Layout

| Path             | What it holds                                                                                         |
| ---------------- | ----------------------------------------------------------------------------------------------------- |
| `src/`           | The app, one folder per feature: `workspace`, `editor`, `project`, `share`, `community`, `cloud`, ... |
| `src/store/`     | The local project store: its Drizzle schema, migrations and the store worker                          |
| `worker/`        | The Cloudflare Worker: routes, D1 repositories, auth, cloud sync, runtime assets, the AI chat relay   |
| `drizzle/`       | D1 migrations, generated by Drizzle Kit from `worker/schema.ts`                                       |
| `examples/`      | Official examples: `example.json`, the project `files/` and the build-time `recording.json`           |
| `guides/`        | Guided walkthroughs: `<slug>/guide.ts`, compiled to `guide.json`, with per-step recordings            |
| `og/`            | The link preview cards, drawn at build time                                                           |
| `scripts/`       | Local server, D1 migrate and seed, guide and example generators, the release                          |
| `e2e/`           | The Playwright suite, run from the repository root                                                    |
| `wrangler.jsonc` | Worker bindings: D1, the two R2 buckets, the rate limits and the Durable Objects                      |

## Projects and runs

Local projects live in this browser's store: an SQLite database in the origin private file system (OPFS), run by
sqlite-wasm in a store worker. Tabs share it through a Web Lock. A project record holds a `RunManifest` (the dialect,
the release pair, the files, the entrypoints and synthetic environment values), or for a side-by-side project a pair
manifest with them per side. Records the app cannot read, such as
one on a removed release pair, stay in the store for recovery or export instead of being reset. Autosave waits 500 ms;
a failed save keeps the edit in memory and offers Retry. Export JSON to back up or move projects to another browser.

If another tab removes a project while this tab has pending edits, those edits become a new Local copy. A notice
links to the copy. The original stays removed; the recovered copy has its own ID and no Cloud association.

The app checks the browser before loading the editor or the runtime. Run captures the manifest at that moment, so
later edits do not change a run in progress. Cancel and project switching discard late results and wait for the
runtime to clean up. Debug capture, off by default, can export state snapshots, events, SQL, timings and diagnostics.

### Displaying query results

Project code gets an injected `$.display` helper, with no import:

```ts
const users = await db.select().from(schema.users);
$.display("Users", users);
$.display("Summary", { count: users.length });
// Multiple values share one label, in the order supplied:
$.display("Overview", users, [{ total: users.length }]);
```

Each call adds a labeled section to Results. Arrays of objects render as tables, other values as trees. Values are
captured at the time of the call, so output already captured stays when a later statement fails. A default export
also works and shows separately.

### Changing the local store schema

1. Edit `src/store/schema.ts`.
2. Run `pnpm db:generate:store` from the repository root. Kit writes `src/store/migrations/<timestamp>_<name>/`.
3. Kit drops `NOT NULL` from TEXT primary keys in SQLite; add it back by hand in the new `migration.sql`.
4. Run `pnpm db:check:store` (`pnpm db:check` and CI run it too). It applies every migration to an empty SQLite file
   and fails when `drizzle-kit push --explain` still plans a change.

The app bundles the migrations, and the store worker applies them when it opens the database.

## Official examples and guides

Run the commands in this section from the repository root.

Official examples live in `examples/<slug>/`; `pnpm --filter @drizzle-run/app generate:examples` indexes them for the
Worker. A side-by-side example lists its two sides in `example.json` (`"sides": [{ "name": "SQL-like" }, { "name": "RQB" }]`). Each side runs
the example's `dialect`, `releasePair` and guest flavor unless it names its own (`"dialect": "sqlite"`, a
`releasePair`, a `guestFlavor`), so any two sides can run together, on one database or both. `files/` holds what both
sides share, the seed included, and `sides/1/` and `sides/2/` what each side runs on its own; sides on two databases
each keep their own schema there.

Guides live in `guides/<slug>/guide.ts`; `pnpm --filter @drizzle-run/app generate:guides` compiles them to `guide.json`.

`pnpm build` runs both generators. `pnpm dev` regenerates guides at startup; after adding or changing an example,
run `pnpm --filter @drizzle-run/app generate:examples` before starting the dev server. CI replays every guide step
on its release pair with `pnpm check:guides`.

Official examples and guide steps carry recordings made at build time, so an embed can show a real run in a browser
that cannot run it. `pnpm record:official` (from the root) runs each one in the built app on Chromium and writes
`examples/<slug>/recording.json` and `guides/<slug>/recordings/<step>.json`. A recording is shown only for exactly
the code and guest it ran on, and `pnpm test` fails when one is missing or stale: after editing an example or a guide,
run `pnpm record:official` and commit the recordings. Set `OFFICIAL_RECORDINGS_FORCE=1` to record every one again.

## Sharing

**Share** publishes a public snapshot after sign-in and explicit consent. The Worker stores published source and
metadata in D1, never a playground database. Shared source and synthetic environment values are visible to anyone
with the link. **Push changes** replaces the stored snapshot at the same shared link. Copying an existing link
does not publish pending edits.

Opening `/s/:id` creates a temporary editable copy and never runs shared code on its own; **Fork to my projects**
saves a copy locally. `/embed/:id` is the compact read-only view that the standalone loader loads in an iframe (see
[embed loader](src/embed-loader/README.md)). The Share dialog gives the embed code, and can include the author's
last run, which embeds show where the browser cannot run the project.

### Community

Ticking **List in Community** in the Share dialog lists the published snapshot on `/community`. Listing needs a
GitHub sign-in, and the card shows the owner's `@login`. A listing is a `playground` or, when **It reproduces a bug**
is ticked, a `bug-repros` entry, with its own filter. The Worker reads the title, each side's database and pair, and the files from
the stored snapshot, never from the request. The database filter matches a side-by-side share on either side's
database, so PostgreSQL vs SQLite lists under both. Pushing changes updates the listing; unticking unlists it.
**Report** on a card only counts reports; moderation is manual ([docs/cloudflare.md](../../docs/cloudflare.md#community-moderation)).

### Link previews

The Worker sets each page's title, description, canonical link and Open Graph tags, and serves `/robots.txt` and
`/sitemap.xml`. A share is indexable only at its latest link while it is listed. The `og:image` cards are drawn at
build time by `pnpm --filter @drizzle-run/app generate:og-images` (Satori and resvg) into `public/og/`, so the Worker
spends no CPU on images:
one card per app page, per official example, and per share topic and side combination, each side a database,
release and flavor, so PostgreSQL vs SQLite has its own (`worker/og-images.ts`). `og/cards.ts` lists them, and a test checks it draws every image the Worker names.

### Sign in with GitHub

An account lets you share links, list them in Community, and sync projects across machines; everything else works
without one. Every share belongs to the account that published it, so it appears in My shares and you can push changes
or stop sharing from any browser where you sign in. Community listing stays optional.
My shares searches them by name, copies each link, and names the project in this browser each one came from; My
projects shows which projects have a link, and who can find it.

Sign-in uses the GitHub web flow with `state` and PKCE. The Worker uses GitHub's token once to read the id, login and
name, then drops it. The session is an opaque `HttpOnly`, `SameSite=Lax` cookie; D1 stores only its SHA-256.
Session checks renew it to 30 days at most once per day, updating both D1 and the cookie. Visible-page activity
triggers a check at most hourly; an idle tab does not keep a session alive. With daily renewal, inactivity expiry
falls between 29 and 30 days after the last check. Expired or revoked sessions require sign-in again.
Setup is in [docs/cloudflare.md](../../docs/cloudflare.md#sign-in-with-github). The e2e suite never
talks to GitHub: it uses a mock in `scripts/github-oauth-mock.ts`.

### Cloud sync

Projects are either **Local** (this browser only) or **Cloud** (your signed-in account). Signing in downloads the
account's Cloud projects without enrolling existing Local projects. When Cloud is available, the new-project dialog
defaults to Cloud and lets you choose Local. **Move to Cloud** enrolls a Local project. **Duplicate as Local** makes
a separate browser-only copy and leaves the original in Cloud.

The app saves edits to the browser first. If a project changes here and on another machine before syncing, it keeps
the edits here and saves the other version as a project named **(copy)**. A notice links to that copy. Offline edits
and edits past an account limit stay in this browser until they can sync.

Deleting a Local project removes it from this browser. **Delete everywhere** removes a Cloud project from the
account and its synced browsers. Duplicating a Cloud project as Local does not delete its account copy.

Signing out removes Cloud copies from this browser and keeps Local projects. The app tries to save pending Cloud
edits first; if it cannot, you can cancel, retry, or explicitly sign out anyway and discard those unsaved Cloud
edits. Automatic session expiry removes saved Cloud copies and keeps unsynced edits as Local. Pending edits in
another tab are recovered as separate Local copies, as described above. Signing back in downloads account copies
again; cleanup does not delete them from the account.

The Worker enforces the limits, and the app shows them on My projects and in Settings:

| Limit                                 | Value          | Past it                                     |
| ------------------------------------- | -------------- | ------------------------------------------- |
| Projects per account                  | 100            | 403 `cloud_project_limit`                   |
| Size per project (its record as JSON) | 1 MiB          | 413 `cloud_project_too_large`               |
| Storage per account                   | 25 MiB         | 403 `cloud_storage_limit`                   |
| Save requests per account             | 100 per minute | 429 `cloud_rate_limited` with `Retry-After` |

Cloud sync starts after 5 s without edits, refreshes on focus or reconnection, and attempts a final save when the
page hides or closes. A closing browser may interrupt network work; check the Cloud status before leaving if you
need the latest edits on another machine. Sync skips a project whose content digest matches the Cloud copy.
Each save names the revision it builds on, and a stale one gets 409 `cloud_conflict`. D1 keeps the index;
the `CLOUD_PROJECTS` R2 bucket keeps each project at `projects/<user id>/<project id>/<revision>-<uuid>.json`. A save writes
a new key, then deletes the replaced revision, so a lost race never overwrites the winner. Setup is in
[docs/cloudflare.md](../../docs/cloudflare.md#cloud-sync).

## Monaco clipboard patch

The workspace applies [a pnpm patch](../../patches/monaco-editor@0.57.0.patch) to Monaco 0.57.0 for
[a WebKit clipboard cancellation error](https://github.com/microsoft/monaco-editor/issues/5458). It observes rejection
of a deferred clipboard payload that Safari may abandon. The package version stays pinned, and
`e2e/clipboard.e2e.ts` checks that cancelling pending writes does not produce an unhandled rejection. Recheck the
upstream fix and this regression before removing the patch during a Monaco upgrade.

## Local HTTPS for iPhone testing

A phone reaches the dev server by the Mac's LAN IP. The runtime needs HTTPS because browsers make
`SharedArrayBuffer` available only on secure pages.

Run these commands from the repository root:

1. Initialize local services with `pnpm dev`. Wait for the local server URL, then stop it with Ctrl-C. This builds the
   packages, applies D1 migrations, and uploads runtime assets to local R2. Repeat after changing runtime packages or
   guest versions.
2. With [mkcert](https://github.com/FiloSottile/mkcert) installed, create a certificate for your Mac's LAN IP:

   ```bash
   mkcert -install
   mkdir -p .cache/local-https
   mkcert -key-file .cache/local-https/dev-key.pem -cert-file .cache/local-https/dev.pem <LAN IP> localhost 127.0.0.1 ::1
   ```

   Repeat the certificate command when the LAN IP changes.

3. On the iPhone, install the public `rootCA.pem` from the folder printed by `mkcert -CAROOT` (AirDrop works). Enable
   full trust in Settings > General > About > Certificate Trust Settings. Keep `rootCA-key.pem` and the development
   private key on your Mac.
4. Start the HTTPS server:

   ```bash
   pnpm --filter @drizzle-run/app dev:https
   ```

5. Open `https://<LAN IP>:5173` on the iPhone, on the same network as your Mac. The server uses port 5173 and fails
   when that port is taken.

HTTP and HTTPS have separate browser storage. Export and import projects to move them between origins.
